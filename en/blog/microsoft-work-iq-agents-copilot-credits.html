Microsoft Work IQ: Understanding Agents, Microsoft 365 Data and Copilot Credits

Understand how Microsoft Work IQ supports Copilot and agents, how different agents access Microsoft 365 data, and when Copilot Credits may be consumed.

Microsoft 365By MC3 Cloud Team28 October 2026

Two agents can answer the same question using company data while relying on very different architectures and consumption models.

One might run directly inside Microsoft 365 Copilot. Another might run through Copilot Studio or a custom application.

From the user's perspective, both can look very similar. Behind the scenes, however, they may access data differently, use different tools and follow different licensing or consumption models.

Understanding this starts with separating Microsoft 365 data, the mechanisms used to access that data, and the intelligence layer provided by Work IQ.

What is Work IQ?

Work IQ is the intelligence layer that helps Microsoft 365 Copilot and agents understand a user's work context.

It draws on information available across Microsoft 365 and connected applications, including emails, files, conversations, meetings, people and projects, to provide Copilot and agents with relevant context.

Work IQ is built around three areas:

  • data, from Microsoft 365 and connected applications;
  • memory, which provides context about the user and their work;
  • inference, which allows the system to reason over that context and use available tools.

Work IQ should not be confused with Microsoft Graph.

Microsoft Graph gives applications access to Microsoft 365 data and relationships through APIs. Work IQ builds on work context to help Copilot and agents reason and use the appropriate tools.

Work IQ does not give an agent access to everything

Work IQ does not bypass Microsoft 365 permissions.

When an agent operates in a user's context, the information it can access depends on that user's permissions.

Two employees can therefore ask the same agent the same question and receive different answers based on what each person is allowed to access and their individual work context.

This is important from a governance perspective. Copilot and agents can make information that a user already has access to much easier to discover.

Overly broad SharePoint permissions, incorrectly shared files and outdated access rights should therefore be addressed before Copilot and agents are deployed at scale.

Not every agent accesses Microsoft 365 data in the same way

There are several ways for an agent to work with Microsoft 365 information:

  • Work IQ built into Microsoft 365 Copilot;
  • knowledge sources such as SharePoint;
  • Copilot connectors;
  • tools associated with Outlook, Teams, OneDrive, SharePoint or Calendar;
  • Microsoft Graph;
  • Power Platform connectors;
  • Work IQ APIs and tools;
  • business APIs and external services.

These approaches are not interchangeable, and some can be combined.

For example, an agent accessing documents stored in SharePoint does not necessarily mean that it is calling a Work IQ API.

This is one of the main reasons why two agents that look similar to the user can have very different architectures behind them.

Agent Builder: the straightforward way to create an agent in Microsoft Copilot

Agent Builder provides a simple way to create declarative agents from Microsoft Copilot.

The author defines the agent's instructions and the knowledge sources it can use, such as SharePoint sites or information available through Copilot connectors.

This approach works well for straightforward internal scenarios such as:

  • answering questions from sales procedures;
  • supporting team onboarding;
  • finding information in an internal knowledge base;
  • answering questions from a defined set of company information;
  • applying company-specific guidance.

For a user with a Microsoft 365 Copilot licence, using these agents within Microsoft Copilot may be covered by that licence depending on the capabilities being used.

Different conditions can apply to users without a Microsoft 365 Copilot licence, particularly when an agent uses shared organisational data.

Agent Builder is intentionally simple. When the scenario requires more advanced actions, connectors or workflows, the agent can be moved into Copilot Studio.

Copilot Studio can use different architectures

Copilot Studio goes further by combining knowledge, tools, connectors, workflows and different publishing channels.

However, not every Copilot Studio agent works in the same way.

An agent can use tools associated with individual Microsoft 365 services such as Mail, Teams, SharePoint or OneDrive.

It can also use Work IQ to take advantage of context across multiple Microsoft 365 services.

In the newer Copilot Studio experience based on the GitHub Copilot harness, Work IQ can be used by supported agents. This architecture uses a consumption model based on Copilot Credits.

Other Microsoft 365 tools remain available in architectures based on the standard harness, with a different runtime and consumption model.

Knowing that an agent was built in Copilot Studio is therefore not enough. You also need to understand which tools it uses and how it runs.

An autonomous agent is not the same thing as a Work IQ agent

Agent autonomy and Work IQ are separate concepts.

An autonomous agent can perform tasks with less human intervention based on its instructions, triggers and available tools.

For example, it may use:

  • Work IQ;
  • Power Platform connectors;
  • Microsoft Graph;
  • Dataverse;
  • business APIs;
  • workflows;
  • or a combination of these components.

Using Work IQ does not automatically make an agent autonomous. An autonomous agent does not necessarily need Work IQ either.

Autonomy can, however, affect consumption when an agent performs many operations, calls several tools or uses capabilities that are billed based on usage.

The cost therefore depends on what the agent actually does rather than simply whether it is described as autonomous.

Native Work IQ and Work IQ APIs are not the same model

One of the most important distinctions is between Work IQ built into Microsoft 365 Copilot and Work IQ used as a service by an application or agent.

Within Microsoft 365 Copilot, Work IQ is part of the experience available to appropriately licensed users.

Microsoft also provides Work IQ APIs and tools that allow custom applications and agents to use this intelligence.

This second model is consumption-based and can use Copilot Credits.

Work IQ APIs should also be distinguished from Microsoft 365 Copilot APIs. Although both can be used to build experiences around Microsoft 365 and Copilot, their use cases, requirements and consumption models are not necessarily the same.

When can Copilot Credits be consumed?

Copilot Credits can be consumed when an agent or application uses capabilities that are billed based on usage.

Examples can include:

  • a Copilot Studio agent using Work IQ with the GitHub Copilot harness;
  • an application or agent calling Work IQ APIs;
  • certain agent scenarios involving users without a Microsoft 365 Copilot licence;
  • some advanced Copilot Studio capabilities;
  • certain AI Builder functions or models.

By contrast, Microsoft 365 Copilot experiences included with the appropriate Microsoft 365 Copilot licence are covered by that licence.

It is therefore misleading to think of every question sent to Copilot as having a fixed cost in Copilot Credits.

Consumption depends on the experience, runtime, models, tools and operations involved.

Why can two similar agents have different costs?

Consider two agents that answer questions about a sales procedure stored in SharePoint.

The first is built with Agent Builder and used from Microsoft Copilot by an employee with a Microsoft 365 Copilot licence. Its use may be covered by that licence depending on the capabilities involved.

The second is built in Copilot Studio, uses Work IQ through a consumption-based architecture and may also call other tools or workflows. Running it can therefore consume Copilot Credits.

To the user, both agents appear to be doing the same thing: searching SharePoint.

Behind the interface, they may use different architectures, runtimes, tools and consumption models.

The mistake to avoid

Do not determine the expected cost of an agent simply from its name or where it was created.

Before moving an agent into production, check:

  • where the agent is built and where it runs;
  • whether its users have Microsoft 365 Copilot licences;
  • which knowledge sources it uses;
  • which tools and connectors are enabled;
  • whether Work IQ is involved;
  • which Copilot Studio runtime is being used;
  • whether the agent calls Work IQ APIs;
  • which capabilities can consume Copilot Credits;
  • how consumption is monitored;
  • whether Microsoft 365 permissions and access to business applications are properly governed.

This becomes particularly important for agents that can perform many operations without continuous human interaction.

Which approach should you choose?

There is no single architecture that is right for every scenario.

  • Agent Builder works well when you need a straightforward declarative agent inside Microsoft Copilot.
  • Copilot Studio is better suited to scenarios requiring connectors, workflows, business tools, greater control or additional publishing channels.
  • Work IQ in Copilot Studio is relevant when an agent needs to take advantage of work context across Microsoft 365 services.
  • Work IQ APIs and tools are designed for scenarios where Work IQ capabilities need to be integrated into a custom application or agent.
  • An autonomous architecture makes sense when a process needs to progress with less human intervention, provided that tools, permissions and consumption are properly controlled.

What to remember

Work IQ is not a database, a connector or a new name for Microsoft Graph.

It is the intelligence layer that helps Microsoft 365 Copilot and agents understand work context and use the information and tools they are authorised to access.

Two agents can therefore provide a very similar user experience while relying on completely different architectures and consumption models.

Before choosing an architecture, ask four questions: where will the agent run, what data will it use, which tools will it call, and which licensing or consumption model will apply?
